## Exploration: Paginate List Slugs

### Current State

The `GET /slugs` endpoint was implemented in a previous change (`list-slugs`) and returns ALL slugs as a flat JSON array. The implementation follows a clean three-layer Go architecture (Handler → Service → Store) with sqlc-generated SQLite queries and Chi router.

Two review findings prompted this exploration:

1. **Warning — Unbounded query**: `ListSlugs` SQL has no `LIMIT` clause. With enough data, a single request returns every row in the `urls` table, risking OOM and slow responses.

2. **Info — Missing error wrapping**: `Service.ListSlugs` at `service.go:119` passes through the raw store error:
   ```go
   func (s *Service) ListSlugs(ctx context.Context) ([]SlugEntry, error) {
       return s.store.ListSlugs(ctx)
   }
   ```
   Unlike `GetStats` and `CreateShortURL` which wrap with `fmt.Errorf("failed to get stats: %w", err)`, this provides zero stack context — the caller gets a raw sql error with no service-layer context.

### SQLite Limits Considered

The database is SQLite. Practical constraints:
- SQLite default max page count = ~140TB theoretical, but practical limit for a URL shortener is far lower
- `OFFSET` in SQLite scans and skips rows — no index-based offset optimization
- Even at 100K rows, a full scan of slug/original_url/click_count/created_at is ~20-50MB JSON response
- **Key insight**: SQLite's locking model means long-running SELECTs block writes (deferred transactions mitigate this but it's a real concern)

### Response Format — Breaking Change Required

Current response is a flat JSON array. With pagination, the format MUST change to include navigation metadata. The new shape:

```json
{
  "data": [
    { "slug": "xyz99", "original_url": "https://...", "click_count": 0, "created_at": "..." }
  ],
  "pagination": {
    "page": 1,
    "limit": 50,
    "total": 100,
    "total_pages": 2
  }
}
```

This is a breaking change to the existing `GET /slugs` response. Since the project is fresh (config says "fresh project"), no real consumers should be depending on the current flat-array format. The spec (`openspec/specs/url-listing/spec.md`) and all tests will need updating.

### Approaches

1. **Offset-based pagination — `?page=1&limit=20`** (Recommended)
   - Query params: `page` (default 1), `limit` (default 50, max 200)
   - Two SQL queries per request: one with `LIMIT ? OFFSET ?` for data, one `SELECT COUNT(*)` for total
   - Response: envelope with `data` array + pagination metadata
   - Pros: Industry standard, easy for clients, enables "jump to page N", SQLite's second query for COUNT is fast
   - Cons: OFFSET drift on concurrent inserts (rows shift between pages); OFFSET gets slower at high page numbers (SQLite must scan skipped rows); two queries per request
   - Tradeoff mitigated: URL shortener data is append-mostly; OFFSET drift is acceptable. SQLite at this scale handles OFFSET well up to tens of thousands
   - Effort: Medium

2. **Cursor-based (keyset) — `?cursor=2025-01-01T00:00:00Z&limit=20`**
   - Query params: `cursor` (opaque `created_at` value), `limit` (default 50)
   - SQL: `WHERE created_at < ? ORDER BY created_at DESC LIMIT ?`
   - Separate query for first page (no cursor)
   - Pros: Stable pagination under concurrent writes; no OFFSET performance degradation; cursor encodes state
   - Cons: Cannot "jump to page N"; cursor format tied to `created_at` column; more complex client logic; ties pagination strategy to sort column
   - Effort: Medium-High

3. **Simple LIMIT (no pagination metadata) — `?limit=50`**
   - Query params: `limit` only (default 0 = no limit, for backward compat)
   - SQL: `LIMIT ?` when limit > 0
   - Response: same flat JSON array (backward compatible)
   - Pros: Minimal change, fully backward compatible, solves the OOM risk
   - Cons: No way to get "the next page" without metadata; clients can only get "first N" or "all"; doesn't solve the unbounded-response UX problem; no pagination envelope means clients can't know total count
   - Effort: Low

4. **Combined — default flat array, envelope when params present**
   - No params: return flat array (backward compat)
   - Params present: return pagination envelope
   - Pros: Backward compatible by default
   - Cons: Two response shapes from same endpoint (confusing API contract); adds branching complexity in handler; clients must handle both response shapes
   - Effort: Medium

### Recommendation

**Approach 1 — Offset-based pagination with `page` and `limit` query params.**

Rationale:
- **Standard API pattern**: Every developer knows how to use `page`/`limit`. No learning curve.
- **Fresh project**: Breaking the response format now is acceptable — no real consumers yet. Waiting would make the breaking change harder.
- **Addresses both findings**: The new service method will wrap errors with `fmt.Errorf`, fixing the info finding.
- **Two SQL queries**: The `COUNT(*)` query is fast in SQLite (reads index directly), and the `LIMIT/OFFSET` query is correct for this access pattern.
- **Default values protect against unbounded responses**: Even without query params, the query uses a default limit.

Query params:
| Param | Type | Default | Max | Description |
|-------|------|---------|-----|-------------|
| `page` | int | 1 | - | 1-indexed page number |
| `limit` | int | 50 | 200 | Items per page |

Response envelope:
```json
{
  "data": [
    {
      "slug": "abc12",
      "original_url": "https://example.com",
      "click_count": 5,
      "created_at": "2025-07-05T12:00:00Z"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 50,
    "total": 100,
    "total_pages": 2
  }
}
```

Error wrapping — new service method:
```go
func (s *Service) ListSlugs(ctx context.Context, page, limit int) (*PaginatedSlugs, error) {
    if page < 1 {
        page = 1
    }
    if limit < 1 || limit > 200 {
        limit = 50
    }

    offset := (page - 1) * limit
    total, err := s.store.CountSlugs(ctx)
    if err != nil {
        return nil, fmt.Errorf("failed to count slugs: %w", err)
    }

    entries, err := s.store.ListSlugsPaginated(ctx, limit, offset)
    if err != nil {
        return nil, fmt.Errorf("failed to list slugs: %w", err)
    }

    totalPages := (total + int64(limit) - 1) / int64(limit)

    return &PaginatedSlugs{
        Data: entries,
        Pagination: PaginationMeta{
            Page:       page,
            Limit:      limit,
            Total:      total,
            TotalPages: int(totalPages),
        },
    }, nil
}
```

### Risks

- **Breaking change to response format**: The spec and all tests must be updated. Mitigation: the config says "fresh project" — no real consumers should be affected. Archive the old `list-slugs` change and update the spec.
- **Two SQL queries per request**: Adds latency for the COUNT query. Mitigation: SQLite COUNT on a primary key index is sub-millisecond at this scale. If it becomes an issue, cache the count.
- **OFTSET drift on concurrent inserts**: New rows inserted between page requests can shift entries. Mitigation: this is an append-mostly workload; drift is acceptable. If needed later, switch to cursor-based pagination.
- **OFFSET performance at high page numbers**: SQLite must scan and discard skipped rows. Mitigation: cap `max(limit) * page` implicitly via sensible defaults. At 100K rows and page=2000, OFFSET is still fine. If scale grows, migrate to cursor-based.

### Ready for Proposal

Yes — the approach is clear, the breaking change is acceptable for a fresh project, and both review findings are addressed. The proposal should flag the response format change as the key decision point for the user, since existing tests and the spec must be updated.
